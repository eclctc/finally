## UI Considerations

Applicable state considerations resolved: 22 covered, 5 backstop, 0 unresolved. Researcher classification: transcript = `list-collection`; message bubble = `static-content`; composer = `form`; Send button, quick-prompt chip, collapse toggle = `interactive-control`; action chip list = `list-collection`; loading line and error block = `static-content`. The probe engine (run by the orchestrator after checker approval) may re-raise checks; its rows replace these.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | transcript | ✅ covered | With no messages and no pending or failed attempt, the transcript shows `Ask FinAlly about your portfolio.` and the three quick-prompt chips. The composer stays visible below. |
| loading | transcript / reply | ✅ covered | While `POST /api/chat` is in flight the user's bubble is already shown, followed by `Thinking...` (`chat-loading`, `role="status"`). The element is absent from the DOM when idle, after success and after error. |
| error | transcript / reply | ✅ covered | A failed send renders the error block (`chat-error`, `role="alert"`) under the user's bubble, keeps the composer text, and re-enables Send. See "Send lifecycle". |
| populated | transcript | ✅ covered | Messages stack top to bottom in send order; the transcript owns its scroll (`min-h-0 flex-1 overflow-y-auto`) and auto-scrolls to the newest item. |
| overflow | transcript | ✅ covered | Many messages scroll inside the transcript; the panel and the page never grow. A new message or the loading line scrolls into view with `scrollIntoView({ block: "end" })` (instant, no smooth behavior, so reduced motion needs no special case). |
| long-text | message bubble | ✅ covered | `whitespace-pre-wrap break-words` and `max-w-[85%]`: a long unbroken string or a long ticker list wraps inside the bubble and never causes horizontal scroll. |
| long-text | action chip | ✅ covered | `break-words` and full bubble width: a long failure reason wraps onto further lines; chip height grows, nothing is truncated. |
| zero-one-many | action chips | ✅ covered | An assistant reply with zero actions renders no action list (no empty container). One or several (up to 10: 5 watchlist + 5 trades, plus skipped ones) render as a vertical list in the returned order. |
| zero-one-many | chat messages | ✅ covered | Zero shows the empty state; one or many use the same bubble layout. No singular/plural copy. |
| partial | action chips | ✅ covered | A reply with mixed outcomes renders each action with its own `data-status`; a reply whose actions all failed still shows the assistant text plus red chips and does NOT trigger a refresh or highlight. |
| partial | assistant reply | ✅ covered | A reply with an empty `message` string still renders its assistant bubble (so the reply count stays +1 and the action chips have an anchor); the bubble holds only the hidden sender name. |
| loading | Send button | ✅ covered | Disabled (`opacity-50 cursor-not-allowed`) while a request is in flight; Enter and chip clicks are ignored while in flight; the label stays `Send`. |
| empty | Send button | ✅ covered | Disabled while the trimmed composer text is empty; Enter on empty text does nothing. |
| loading | composer textarea | ✅ covered | `readOnly` (not `disabled`) while in flight, with `opacity-60`, so focus is not lost and the text cannot change between send and reply. |
| error | composer textarea | ✅ covered | The text is kept after a failed send; editing it after a failure is allowed; the error block remains until the next send starts. |
| long-text | composer textarea | ✅ covered | The 56px textarea scrolls its own content; no `maxLength`; no auto-grow (the panel layout never shifts while typing). |
| loading | quick-prompt chips | ✅ covered | Chips are disabled (`opacity-50`) while a request is in flight. In the empty state the first chip click starts a request immediately, so chips are only ever seen disabled in the brief overlap. |
| populated | quick-prompt chips | ✅ covered | Chips render only in the empty state (no messages, no attempt). They disappear once the first send starts and do not return in the session. |
| error | collapse toggle | ✅ covered | The toggle has no failure mode. |
| partial | collapsed panel | ✅ covered | While collapsed the transcript, composer draft, in-flight request, pending text and error are all retained (state lives above the panel body). A reply that arrives while collapsed is present on expand; the refresh and highlight still run. |
| overflow | collapsed rail | ✅ covered | The rail is a fixed 40px column holding a glyph and an 11px vertical label; nothing wraps. |
| populated | highlighted rows | ✅ covered | See "AI-change highlight": rows that exist after the post-reply refresh and were touched by a successful action carry `data-ai-changed="true"` for a bounded window; rows that no longer exist (a removed ticker, a closed position) get nothing. |

### Panel structure (open)

`section` (`data-testid="chat-panel"`, the existing Panel chrome: `flex min-h-0 flex-col border border-line bg-panel`, `aria-labelledby` the title `h2`), top to bottom:

1. Title strip, 32px: `AI Chat` (`h2`) and, right-aligned (`ml-auto`), the collapse toggle (`size-6`, `›`, `text-muted hover:text-text`, `focus-visible:outline-2 outline-primary`).
2. Transcript: `role="log"`, `aria-label="Conversation"`, `min-h-0 flex-1 overflow-y-auto bg-surface p-2`, content is a column with `gap-2`. A zero-height sentinel is the last child and is the `scrollIntoView` target.
3. Composer: `form`, `flex shrink-0 gap-2 border-t border-line bg-panel p-2`. Textarea (left, `min-w-0 flex-1`) and Send (right, `self-end`).

The shared `Panel` has no slot for a title-strip control. Add one optional prop, `actions?: React.ReactNode`, rendered inside the title `header` after the `h2` with `ml-auto`. Existing callers pass nothing and are unaffected. (This touches `Panel.tsx`, which Phase 4 may also edit; the change is additive.)

### Collapsed rail

When collapsed, the section keeps `data-testid="chat-panel"` and `aria-label="AI Chat"` (no title strip), and its entire body is one full-height button:

- `button` `flex h-full w-full flex-col items-center gap-2 pt-2 text-muted hover:text-text focus-visible:outline-2 outline-primary`, `aria-expanded="false"`, `aria-label="Expand AI Chat"`, `title="Expand AI Chat"`, `data-testid="chat-toggle"`.
- Children: the glyph `‹` (Body), then the label `AI Chat` as 11px / 600 text with `[writing-mode:vertical-rl]`.

The aside becomes `w-10`; the main region (`flex-1`) absorbs the freed 280px, so the center grid's fluid columns widen. No min-width rule is violated (the page minimum stays 1280px). Collapse state is session-only and is not persisted (layout persistence is out of scope); a reload opens the panel.

The open-state toggle carries the same `data-testid="chat-toggle"`, `aria-expanded="true"`, `aria-label="Collapse AI Chat"`. There is exactly one `chat-toggle` in the DOM at a time.

### Collapse and focus behavior

- Collapse and expand are instant (no width animation), consistent with "no motion that is not data".
- On collapse, focus moves to the rail button (the old toggle no longer exists). On expand, focus moves to the composer textarea. Both are the only places focus is programmatically moved in this phase.
- The conversation, composer draft, pending request and error are held by a chat state hook mounted ABOVE the panel body (in `Dashboard` or a `ChatDock` wrapper), so unmounting the open body on collapse loses nothing. This satisfies CHAT-01 "collapsing and reopening keeps the conversation".
- No unread indicator on the rail in v1 (Decision D-06).

## Chat Panel Contract

### Messages

- `chat-message` elements are exactly the user and assistant bubbles and nothing else (loading line, error block, chips and action chips are NOT `chat-message`). `data-role="user"` or `data-role="assistant"` on each. The spec counts assistant `chat-message` elements, so no duplicate bubble may ever exist for one reply.
- Each bubble starts with a visually hidden sender name (`<span className="sr-only">You </span>` / `FinAlly `) followed by the message text node.
- User bubble: right-aligned (`ml-auto`), `max-w-[85%]`, `border border-line bg-surface px-2 py-1 text-text`. Because the transcript well is also `surface`, the 1px `line` border is what draws the bubble (Deviation #2).
- Assistant bubble: left-aligned, `max-w-[85%]`, `border border-line bg-panel px-2 py-1 text-text`.
- Corners are square (`rounded-none`, the default), matching the terminal look of the rest of the app. No avatars, no timestamps (session-only history, dense layout).
- Message text: `whitespace-pre-wrap break-words`. Assistant text is plain text; markdown, HTML and links are not interpreted.

### Action chips (CHAT-03)

- Directly under the assistant bubble that produced them, as a `ul` (`aria-label="Actions"`) with `mt-1 flex max-w-[85%] flex-col gap-1`. Absent when the reply has zero actions. One `li` per action, in the order the backend returned them (watchlist changes first, then trades).
- Each `li` is `data-testid="chat-action"` with `data-status="ok"` or `data-status="failed"`.
- Executed: `border border-line bg-surface px-2 py-1 text-text`, Label 11px / 400, `.figures`, `break-words`.
- Failed: same box with `border-down/50 text-down`. The word `failed` and the reason are in the text, so color is never the only signal.
- A chip shows the attempted action and its outcome in one line (copy table). A trade chip for a fractional quantity uses `formatQuantity` (up to 4 decimals, trailing zeros trimmed). A watchlist ticker is upper-case.
- Chips are not interactive (no hover, no tab stop, no click to select the ticker). They are a log of what happened.

### Send lifecycle (CHAT-02, CHAT-04)

State shape (visual consequence): the transcript holds committed messages plus at most one **attempt slot** at its tail. The attempt slot is the user's text for the current or last failed send.

1. Idle: composer enabled, Send enabled when the trimmed text is non-empty.
2. User presses Send, Enter (without Shift, and not while an IME composition is active) or a quick-prompt chip:
   - The attempt slot appears: the user's bubble (`data-role="user"`) followed by `Thinking...` (`chat-loading`).
   - Send is disabled and the textarea becomes `readOnly`. The text is NOT cleared yet.
   - Enter while in flight is ignored.
3. Success: the attempt slot is replaced by the committed user bubble and the assistant bubble (with its action chips); `chat-loading` leaves the DOM; the textarea is cleared and made editable; focus stays in (or returns to) the textarea. Then the refresh and highlight run (below).
4. Failure: `chat-loading` leaves the DOM; the user's bubble stays; the error block (`chat-error`) appears under it; the textarea keeps its text and becomes editable again; Send is enabled again. The failed attempt is NOT committed to the conversation, because the backend stores nothing on a 502.
5. Resend after failure: the attempt slot is reset (the old bubble and error are replaced by the new attempt's bubble and `Thinking...`), so a retried message never appears twice.

Quick-prompt chip click: set the composer text to the chip label and send immediately (one click asks the question). It overwrites any draft, which is acceptable because chips only exist in the empty state. Because the text is in the composer, the failure follow-up `Your message was kept. Press Send to try again.` is true for chips as well.

Keyboard: Enter sends, Shift+Enter inserts a newline. Tab order: transcript (scrollable, `tabIndex={0}` so keyboard users can scroll it), textarea, Send, then the collapse toggle comes earlier (it sits in the title strip, before the transcript).

### Error block (CHAT-04)

`chat-error` is a `div` with `role="alert"`, assistant-aligned (`max-w-[85%]`), `border border-down/50 bg-panel px-2 py-1`, containing the error text (`text-down`) and, as a second block element, the follow-up line (`text-muted`). It is a React text node render of the backend string. It is not a `chat-message` and not persisted in the conversation. No retry button: Send is the retry (P1 copy says so).

### Composer

- Textarea: `h-14 min-w-0 flex-1 resize-none border border-line bg-surface px-2 py-1 text-text`, placeholder `Message FinAlly` in `text-muted`, `data-testid="chat-input"`, `aria-label="Message to FinAlly"`, `autoComplete="off"`, `spellCheck={false}`. Focus: `border-primary`, no glow. Autofocus is NOT set (the page's first focus should not jump into the chat).
- Send: `data-testid="chat-send"`, `type="submit"`, `h-7 self-end bg-submit px-4 font-semibold text-white`, hover `brightness-110`, disabled `opacity-50 cursor-not-allowed`, `focus-visible:outline-2 outline-primary`.
- Submit goes through the form so both Enter and the button share one path.

### Quick-prompt chips (CHAT-06)

- Shown under the empty line, only in the empty state: `flex flex-wrap justify-center gap-2 px-2`.
- Each is a `button type="button"`, `data-testid="chat-chip"`, `h-7 border border-line bg-panel px-2 text-text hover:border-primary focus-visible:outline-2 outline-primary`, disabled `opacity-50`.
- They are never purple, never green or red, and carry no icon.

### Live region and announcements

- The transcript is `role="log"` (implicit polite live region), so new assistant replies are announced once as they are appended. The loading line is `role="status"`. The error block is `role="alert"`. Nothing else announces.

## AI-change highlight (CHAT-05)

### Trigger

After a chat reply resolves, if at least one action has `status: "ok"`:

1. Refresh, in parallel: the watchlist (`useWatchlist.load` path, so row membership and `seedPrices` update), the portfolio (`usePortfolio.refresh`, which feeds the header cash and total and the positions table and heatmap) and the P&L history (`/api/portfolio/history`).
2. When that refresh has settled, mark the rows the AI changed (below). If the refresh fails, mark nothing; the chat reply is still shown.

If every action failed, or the reply had no actions, nothing is refreshed and nothing is highlighted. A refresh failure shows no new UI of its own (the existing header and watchlist failure alerts already cover load failures).

AI removals must clean the price store the same way a manual removal does (Phase 3: `clearTicker`), so a ticker the AI removes and later re-adds does not draw a sparkline across the gap.

### Which rows

| Action (status ok) | Highlighted row |
|--------------------|-----------------|
| watchlist `add` | the `watchlist-row-{T}` for that ticker (including an idempotent add of an already watched ticker) |
| watchlist `remove` | nothing (the row is gone) |
| `buy` or `sell` | the `position-row-{T}` for that ticker, if it still exists after the refresh (a sell that closes the position removes the row, so nothing is highlighted) |

Not highlighted: heatmap tiles, the P&L chart, the header figures (`total-value` and `cash-balance` never flash, Phase 3 D-09), failed actions, and the chat's own chips. The watchlist row of a traded ticker is NOT highlighted (the trade changed a position, not the watchlist).

### Visual

| Property | Value |
|----------|-------|
| Target element | the row's `li` / `tr` itself (whole-row fill), never the price cell, so it cannot be confused with the price flash |
| Color | `bg-primary/20` (token `primary`, no new token, no hex) |
| Why blue, not green or red | A trade or an add is not a price direction. Green and red are reserved for direction and P&L (Phase 1 semantic rules), and the price cell may flash green or red at the same time on the same row. |
| Hold | 1500ms at full strength with `transition-none` (`AI_HIGHLIGHT_HOLD_MS = 1500`) |
| Fade | then `bg-transparent transition-colors duration-1000 ease-out` (1000ms), then the marker is removed |
| Attribute | `data-ai-changed="true"` on the row while the highlight is held or fading (absent otherwise), so tests assert on the attribute, not Tailwind class strings. Use full literal class strings in a lookup (Tailwind cannot detect dynamic class names). |
| Stacking | The price flash is on a child cell and paints over the row fill, so both stay legible. A second AI reply that touches the same row restarts the highlight. |
| `prefers-reduced-motion: reduce` | Keep the highlight (it is information, not decoration) but drop the fade: hold 1500ms, then remove with `motion-reduce:transition-none`. This differs from the price flash, which is dropped entirely, because the highlight lasts long enough to be perceived. |
| Text color | unchanged |

### Dependency on Phase 4 (state, do not fix internals)

- `position-row-{T}` and the Phase 4 refresh path (`usePortfolio` lifted or shared so that the header, positions table, heatmap and P&L chart all refresh from one call) do not exist yet. Phase 5 requires Phase 4 to expose: a way to refresh portfolio plus history on demand (the same call a manual trade uses, TRADE-05), and a way for a positions row to read "AI-changed" (a module store like the price store, or a prop). Phase 5 defines the visual and the attribute; Phase 4 owns the table markup.
- `chat.spec.ts` requires `position-row-AAPL` to be visible right after a mocked buy, so the positions table must refresh from the shared path with no reload.
- If the AI removes the currently selected watchlist ticker, the behavior is whatever Phase 4 defines for a manual removal of the selected ticker; chat adds no extra rule.
- If `04-UI-SPEC.md` defines its own post-trade highlight for manual trades, prefer reusing its mechanism and keep this spec's color and timing for AI changes only.

## Decision Log (confirm in review)

No CONTEXT.md existed and no interactive channel was available. Each decision below was taken with the recommended option. CONFIRM marks the ones most worth the user's attention.

| ID | Decision | Rationale | Alternative |
|----|----------|-----------|-------------|
| D-01 CONFIRM | A quick-prompt chip click sends immediately (sets the composer text, then sends) | One click answers the question; the demo feels fluid. Failure keeps the text in the composer so the P1 follow-up copy stays true. | Chip only fills the composer and waits for Send (two clicks, lets the user edit) |
| D-02 CONFIRM | The composer is cleared only when the reply succeeds; a failed send keeps the text and shows the user's bubble plus the error in a non-committed "attempt slot" that a resend replaces | Satisfies CHAT-04 ("input is not lost") and the backend fact that a 502 stores nothing, with no duplicate bubbles on retry | Clear the composer on send and restore it on error (text vanishes then reappears); or keep a failed bubble in the transcript and allow duplicates |
| D-03 CONFIRM | AI-change highlight is a whole-row `bg-primary/20` fill, 1500ms hold plus 1000ms fade, applied to the watchlist row of an added ticker and the position row of a traded ticker, and starts after the refresh settles | Distinct from the green/red price flash that can run on the same row, no new token, long enough to notice after reading the reply | Reuse green/red 25% (collides with price meaning); also highlight heatmap tiles and the P&L chart (more Phase 4 coupling) |
| D-04 | Executed action chips are neutral, only failures are red | Green means price direction or P&L in this product; a fill is not a gain | Green chips for success (reads as profit) |
| D-05 | Quick-prompt chips show only in the empty state | They are "starter" prompts; the ROADMAP says starter questions; keeps the transcript dense once a conversation exists | Keep a chip row above the composer permanently (costs about 36px of transcript height) |
| D-06 | No unread indicator on the collapsed rail | Refresh and highlight still show the effect of AI actions; one fewer state in a v1 panel | A `bg-primary` 8px dot on the rail when a reply arrives while collapsed |
| D-07 | The input is `readOnly`, not `disabled`, while a request is in flight | Preserves focus and the typed text across the request | `disabled` (loses focus) |
| D-08 | Chat text is rendered as plain text; no markdown | LLM output is untrusted (security rule inherited from Phase 3) and the model is told to be concise | Render a markdown subset (adds a dependency or a parser) |
| D-09 | Textarea (Enter sends, Shift+Enter newline) rather than a single-line input | Phase 1 shared interaction patterns already specify Shift+Enter; analysis questions run long | Single-line `input` (no newline) |
| D-10 | No clear-conversation or retry button | Session-only history needs no clear control; Send is the retry per the reserved copy | Add a `Clear` control later (CHAT-V2) |
