## Flagged Assumptions

- **Open Question 1 resolved: `load()` returns `Promise<boolean>`.** Phase 4's `refresh()` and `refreshHistory()` already resolve a boolean and never reject (Plans 04-01 and 04-06). Making `load` do the same is the simplest way to meet the UI-SPEC sentence "if the refresh fails, mark nothing" as written; Plan 05-04 marks rows only when all three resolve `true`.
- **Lift, not a reload registry (05-RESEARCH Open Question 2).** Phase 4 routes every Watchlist test through `renderWatchlist()` (Plan 04-02), so the lift is a one-helper change.
- **`removedTickers` lives in `chatEffects.ts`, not `chat.ts`.** This keeps `chat.ts` owned by Plan 05-02 in the same wave, so the two plans share no file and run in parallel.
- **WR-02 (unordered loads) is accepted.** A chat reload racing a manual add or remove can briefly apply an older list; the next load corrects it (05-RESEARCH Pitfall 6). No guard is added unless Phase 4 adds one.
- **WR-03 is accepted as in Phase 4.** An AI removal of a held ticker drops its live entry like a manual removal; the next stream frame restores it (Plan 04-02 Flagged Assumptions).
