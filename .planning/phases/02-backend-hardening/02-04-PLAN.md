## Phase Goal

**As a** trader, **I want to** get clean errors and consistent chat actions, **so that** the AI copilot is reliable.

This plan makes a chat turn consistent: one bad action no longer aborts the whole turn, and what the AI says it did always matches what happened.

<objective>
Make every chat action an atomic, independently committed unit, and isolate failures per action (HARD-05). A `savepoint(conn)` helper replaces the connection-level commit block as the unit of work. `execute_trade` and `execute_trade_and_sync` use it, the watchlist writes use it, and a `run_action` wrapper in the chat service turns any failure into a `failed` action. The user and assistant chat rows are stored together with exactly the returned actions.

Purpose: reproduced in research: an `sqlite3.OperationalError` in trade 2 of 3 aborts the turn (the exception propagates, cash 9900.0, zero chat rows). The connection-level commit in `execute_trade` also prevents nesting (a later `RELEASE` fails with "no such savepoint") and its rollback discards unrelated pending work.
Output: the savepoint helper and its tests, savepoint-based services, the chat-service isolation wrapper, and reproduction plus guard tests.
</objective>

## Assumptions

- Open Question 1 (research recommendation, used as the default): per-action committed units through `savepoint(conn)`, not one transaction around the whole turn. A whole-turn transaction would hold a write lock and read snapshot across Massive's `asyncio.to_thread` awaits.
- A6 (research): if the final chat-row insert itself fails (storage-layer failure), the already committed actions stay unrecorded and the request returns 500. Accepted; it needs a storage fault, not an LLM or action fault.
- `UNEXPECTED_ERROR` wording ("Action failed unexpectedly and was not applied") is a public string shown in the chat panel in Phase 5.
- `test_no_transaction_open_during_llm_call` is a regression guard. The criterion already holds today (only SELECTs run before the LLM call), so it is not a reproduction.
